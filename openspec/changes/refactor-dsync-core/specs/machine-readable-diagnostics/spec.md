# Spec Delta

## Purpose

Даёт внешним потребителям (веб-панель, скрипты мониторинга, CI) стабильный
машиночитаемый контракт для состояния флота, диагностики и локального
state-индекса, не заставляя парсить человекочитаемый вывод.

## ADDED Requirements

### Requirement: Единый JSON-конверт диагностических команд

Каждая команда с флагом `--json` (`dsync status`, `dsync doctor`,
`dsync state list`) SHALL выводить ровно один JSON-документ в stdout и не
писать в stdout ничего кроме него. Диагностические сообщения, предупреждения
и прогресс MUST уходить в stderr.

Документ MUST содержать целочисленное поле `schema_version`. Добавление
новых полей в рамках одной версии схемы разрешено; удаление, переименование
или изменение смысла поля MUST сопровождаться увеличением `schema_version`.
Потребители MUST игнорировать неизвестные поля.

#### Scenario: Успешный JSON-вывод

- **WHEN** пользователь запускает `dsync status --json` при доступном хабе
- **THEN** stdout содержит один JSON-объект с `schema_version`, данными о
  машинах и версии хаба
- **AND** в stdout нет строк логов и предупреждений

#### Scenario: Ошибка выполнения

- **WHEN** команда с `--json` не может получить данные (хаб недоступен,
  битый локальный индекс)
- **THEN** команда завершается с ненулевым кодом
- **AND** в stderr выводится причина, а stdout не содержит частично
  сформированного JSON

#### Scenario: Неизвестные поля не ломают потребителя

- **WHEN** новая версия dsync добавила в документ поле, которого нет у
  потребителя
- **THEN** потребитель продолжает разбор, игнорируя неизвестное поле

### Requirement: JSON-статус флота

`dsync status --json` SHALL отдавать снимок флота: версию хаба, карту машин
(имя → online, время последнего push, версия клиента, исходы последних
pull'ов по проектам) и локальную сводку state-индекса (seq, количество
применённых элементов, число failing и dead-letter).

Онлайн-статус MUST вычисляться по тому же порогу, что и в текстовом
статусе, чтобы оба вывода не расходились.

#### Scenario: Две машины, разные версии

- **WHEN** в хабе есть записи о двух машинах, у одной версия клиента
  совпадает с хабом, у другой — отстаёт
- **THEN** JSON содержит обе машины с их `version` и признаком `online`
- **AND** локальная state-сводка присутствует в том же документе

#### Scenario: Упавший pull проекта

- **WHEN** последний SSH-pull проекта на машине завершился ошибкой
- **THEN** в JSON у этой машины есть исход с `ok=false`, числом попыток и
  текстом ошибки

### Requirement: JSON-диагностика окружения

`dsync doctor --json` SHALL отдавать список проверок с устойчивыми
идентификаторами, человекочитаемой меткой, статусом (`ok`, `warn`, `fail`,
`skip`) и деталями, а также версии хаба и клиента и `schema_version`.
Код возврата MUST быть `0`, если нет проверок со статусом `fail`, и
ненулевым, если хотя бы одна проверка провалилась; `warn` сам по себе не
меняет код возврата.

#### Scenario: Все проверки успешны

- **WHEN** конфиг валиден, хаб доступен, ключи и проекты на месте
- **THEN** все элементы списка имеют статус `ok`
- **AND** команда завершается с кодом 0

#### Scenario: Хаб недоступен, конфиг валиден

- **WHEN** хаб не отвечает, но локальные проверки проходят
- **THEN** проверка связности имеет статус `fail`
- **AND** команда завершается с ненулевым кодом
- **AND** остальные проверки всё равно присутствуют в выводе

#### Scenario: Предупреждение без провала

- **WHEN** обнаружен дрейф версий клиента и хаба, но связь и конфиг в порядке
- **THEN** соответствующая проверка имеет статус `warn`
- **AND** код возврата остаётся 0

### Requirement: JSON-сводка локального state-индекса

`dsync state list --json` SHALL отдавать `seq`, количество применённых
элементов и детерминированно отсортированные списки сбойных и dead-letter
элементов с ключом `channel:key`, числом попыток, значением `updated`,
hub-seq и текстом ошибки для dead-letter.

#### Scenario: Есть dead-letter

- **WHEN** локальный индекс содержит элемент, исчерпавший попытки
- **THEN** он присутствует в списке `dead` с причиной и временем попадания
- **AND** списки отсортированы по ключу

#### Scenario: Индекс пуст

- **WHEN** локальный state-индекс отсутствует или пуст
- **THEN** документ содержит нулевые счётчики и пустые списки
- **AND** команда завершается с кодом 0

### Requirement: Секреты не попадают в диагностический вывод

JSON-выводы `status`, `doctor` и `state list` MUST NOT содержать hub-токены,
приватные ключи, passphrase или содержимое payload'ов состояния (снапшоты
tmux, экспортированные сессии). Пути и имена машин выводить разрешено.

#### Scenario: Токен задан в конфиге

- **WHEN** в конфиге присутствует `[hub] token` / `[hub_connect] token`
- **THEN** ни одно поле JSON-вывода не содержит его значение

#### Scenario: Payload состояния не утекает

- **WHEN** в state-индексе есть элементы tmux/opencode
- **THEN** `state list --json` показывает только метаданные и ошибки, но не
  `data`
