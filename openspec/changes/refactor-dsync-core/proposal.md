# Proposal

## Why

`dsync` вырос до ~13 000 строк в 28 файлах: пять модулей перевалили за
1100 строк (`hub/server.rs`, `hub/state.rs`, `client/state.rs`, `tui/ui.rs`,
`tui/cfg.rs`), причём в `hub/state.rs` три четверти файла — встроенные
тесты. Транспорт, доменная логика, персистентность и представление
перемешаны, одинаковые вещи реализованы дважды (TOFU-хранилища хаба и SSH,
два state-индекса, два набора time/retry-хелперов). Из-за этого любая правка
протокола или pull-логики требует держать в голове весь файл, а новые
потребители (будущая веб-панель, скрипты мониторинга) вынуждены парсить
человекочитаемый вывод.

Сейчас подходящий момент: флот небольшой, протокол один (v2), поведение
покрыто 133 тестами, CI зелёный на трёх ОС. Рефакторинг можно делать
поэтапно, без «большого взрыва», сохранив поведение и проводя каждый шаг под
тестами.

## What Changes

- **Разложить крупные модули по границам ответственности** (поведение не
  меняется):
  - `hub/state.rs` → индекс состояния, payload-store (атомарная запись),
    LWW-merge, статус/health;
  - `hub/server.rs` → accept-loop, диспетчер запросов, pull-planner, retry,
    построение remote-команды;
  - `client/state.rs` → локальный индекс, каналы `tmux`/`opencode`,
    collect/apply;
  - `tui/ui.rs`, `tui/cfg.rs` → экраны/виджеты и редактор конфига.
- **Убрать дублирование инфраструктуры**: общий TOFU-store отпечатков
  (hub-сертификат и SSH host-key), общий atomic-write, общий retry/backoff с
  политикой (transient/non-transient), общие time-хелперы, единый POSIX-shell
  quoting и сборка путей для удалённых команд.
- **Единая модель ошибок**: доменные ошибки (`thiserror`) на границах
  hub/client, `anyhow` — только в CLI/init/TUI; в демон-путях нет `unwrap`/
  `expect`/`panic` на достижимых ветках.
- **Машиночитаемые диагностические выходы** (аддитивно, для будущей панели и
  скриптов): `dsync doctor --json`, `dsync state list --json`, стабильный
  `schema_version` в `dsync status --json`. Текстовый вывод по умолчанию не
  меняется. **BREAKING**: нет — новые флаги аддитивны, старые потребители
  продолжают работать.
- **Тесты и CI**: вынести громоздкие unit-тесты из «боевых» файлов; добавить
  интеграционный тест hub↔client поверх QUIC (push → pull-plan → state) и
  snapshot-тесты удалённой shell-команды; зафиксировать поведение на трёх ОС
  (матрица уже есть).
- **Зависимости**: убрать неиспользуемые, свести `dirs`/`directories` к одной,
  оценить обновление `teloxide`/`russh`; `bot` вынести за feature-флаг или
  явно пометить экспериментальным, если обновление откладывается.

**Non-goals**: не менять протокол v2 по смыслу, не добавлять HTTP API в хаб,
не менять поведение push/pull/state, не реализовывать веб-панель (отдельное
изменение `add-fleet-web-ui`), не переписывать TUI.

## Capabilities

### New Capabilities

- `machine-readable-diagnostics`: JSON-контракты `status`/`doctor`/`state list`
  со стабильной схемой, версией и предсказуемыми ошибками — то, на что будет
  опираться веб-панель и внешний мониторинг.

### Modified Capabilities

_(нет — в проекте ещё нет основных спецификаций; поведение протокола не
меняется.)_

## Impact

- **Код**: `src/hub/{server,state}.rs`, `src/client/{state,connect}.rs`,
  `src/tui/{ui,cfg}.rs`, `src/{trust,config}.rs`, `src/ssh/trust.rs`,
  `src/protocol.rs` (только сериализация схем), `src/main.rs`, `src/lib.rs`.
- **CLI**: новые флаги `--json` у `doctor` и `state list`; `status --json`
  получает аддитивное поле `schema_version`.
- **Поведение**: существующие команды и текстовый вывод не меняются; wire-формат
  hub↔client остаётся совместимым с v2 (проверяется тестом).
- **Зависимости**: `Cargo.toml` (удаление/унификация), возможное обновление
  `teloxide`/`russh` отдельным шагом.
- **Риски**: механические переносы кода могут затронуть `#[cfg(test)]`-модули и
  приватность; каждый шаг закрывается `cargo fmt`/`clippy`/тестами, поэтому
  риск локализован.
