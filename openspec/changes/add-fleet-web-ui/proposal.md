# Proposal

## Why

Сейчас флотом управляют только из терминала: `dsync status`/`doctor` на
машине, где есть конфиг и токен, TUI и ручные `push`/`pull`. Чтобы понять,
кто отстал по версии, где упал pull и что в dead-letter, приходится
переключаться между машинами и читать текст. Будущая локальная веб-панель
даст один экран по всем машинам и безопасные действия в один клик.

Предпосылка уже заложена изменением `refactor-dsync-core`
(`machine-readable-diagnostics`): `status`/`doctor`/`state list` получают
стабильный JSON. Панель строится как BFF поверх локального `dsync` CLI —
хаб и его QUIC-протокол не переписываются, секреты не уезжают в браузер.

## What Changes

- Новое приложение **`web/`** в репозитории: Next.js (App Router) + React +
  Tailwind + **shadcn/ui**, pnpm; dev/start слушают `127.0.0.1:3133`.
- **BFF на route handlers**, который на сервере вызывает локальный `dsync`
  (`status --json`, `doctor --json`, `state list --json`, `push`, `pull`,
  `state retry`) без shell-интерполяции; браузер получает только JSON.
- **Экраны**: Dashboard (здоровье флота), Machines (список + детали),
  Projects (матрица машина×проект), State (tmux/opencode, dead-letter),
  Doctor (запуск и результаты), Activity (журнал действий и задач),
  Settings (интервал обновления, тема; только чтение параметров хаба).
- **Действия**: push/pull по машине, повторный state-retry, запуск doctor и
  новый **`dsync deploy --machine <m> [--project <p>] [--force]`** — целевой
  SSH-пулл на машине через хаб (в обход change-detection при `--force`).
  Долгие действия выполняются как фоновые задачи с опросом статуса.
- **Безопасность по умолчанию**: bind только loopback, проверка Origin для
  mutating-запросов, allowlist команд, таймауты, аудит-лог действий, запрет
  вывода секретов и payload'ов состояния.
- **Новый протокол**: запрос `deploy` (hub ↔ client) с токеном; версия
  протокола поднимается до 3, старые сообщения не меняются. Старый хаб
  отвечает ошибкой — панель показывает «требуется обновление хаба».

**Non-goals**: доступ из интернета и многопользовательская аутентификация,
редактирование конфигов из браузера, перезапуск хаба/машин, потоковые логи
и WebSocket, мобильная вёрстка сверх адаптивной сетки, замена TUI.

## Capabilities

### New Capabilities

- `fleet-web-ui`: локальная веб-панель — экраны, обновление данных,
  безопасные действия, состояния ошибок/пустоты, аудит.
- `on-demand-deploy`: целевой запуск SSH-пулла проекта на машине по запросу
  (CLI + хаб), с авторизацией, идемпотентностью и отчётом о результате.

### Modified Capabilities

_(нет — существующих спецификаций в проекте пока нет.)_

## Impact

- **Новый каталог** `web/` (исходники, `package.json`, `pnpm-lock.yaml`,
  `components.json`, конфиг Next.js, README по запуску).
- **CLI**: новая команда `dsync deploy`; `--json`-контракты из
  `refactor-dsync-core` должны быть реализованы до панели (зависимость).
- **Протокол**: `DeployRequest`/`DeployResponse`, `PROTOCOL_VERSION` 2 → 3;
  хаб получает обработчик, клиент — команду. Старые сообщения без изменений.
- **Хаб**: обработчик deploy использует существующий pull-planner с
  `force=true`; аудит в логе хаба.
- **Флот**: приложение не раскатывается автоматически через dsync; ставится
  на одну машину (ноутбук или сервер) вручную/скриптом. Остальные машины
  ничего не получают.
- **Риски**: долгие `post_pull`-сборки в задаче (решаем фоновыми job'ами и
  таймаутами), утечка действия в сеть (loopback + Origin), дрейф версии
  протокола (feature detection и понятная ошибка).
